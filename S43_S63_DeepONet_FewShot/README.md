# S43 + S63 physics-informed conditional DeepONet and few-shot gain estimator

This is a local-first preliminary experiment using three exact Stage 3 PINN
checkpoints:

| Teacher checkpoint | Subject | `Kp_theta` | `Kd_theta` | `Kp_x` | `Kd_x` |
|---|---|---:|---:|---:|---:|
| `s43_chunk1` | S43 | 145.1384 | 15.0346 | 5.0435 | 15.0457 |
| `s63_chunk1` | S63 | 145.109024 | 15.048624 | 14.932888 | 15.048451 |
| `s63_chunk6` | S63 | 197.826233 | 23.354944 | 13.859061 | 23.354867 |

The code is intentionally outside both subject projects. It reads their source
files, gain JSON files, and checkpoints in place. It does not edit or copy the
subject directories.

## What this preliminary experiment asks

The experiment has two linked questions:

1. Can one conditional DeepONet reproduce trajectories generated by the three
   PINN teachers when it receives the initial state, subject descriptors, and
   controller gains?
2. Can a context encoder observe one, two, or four short motion windows,
   estimate the four control gains, and use those estimated gains to reconstruct
   the later trajectory?

This is a proof of concept. Three gain anchors from two human subjects are not
enough to establish continuous gain-space or new-subject generalization.

## Step-by-step methodology

### Step 1 — Resolve the three exact PINN teachers

`validate_setup.py` checks that every teacher has:

- its original unchanged pole-PINN source;
- the requested `stage3_best.weights.h5`; and
- the matching `result.json` containing its four gains, fixed Pi, and delay.

The sweep chunk-1 checkpoints are used directly. They are not assumed to be
identical to the earlier full-run checkpoints.

### Step 2 — Generate a controlled matched teacher dataset

`export_teacher_data.py` creates one common set of initial conditions and asks
all three checkpoints to predict trajectories from exactly those conditions.
The full configuration uses:

- 100 initial conditions;
- a 3.0-second pilot horizon;
- 100 Hz sampling;
- sampled initial angle, horizontal position, angular velocity, and horizontal
  velocity.

The common initial conditions remove one source of confounding: differences
among the three datasets are caused by their learned PINN/checkpoint behavior,
not by using different random initial conditions.

The generated arrays are written under `outputs/teacher_data_full/`. These are
new checkpoint predictions, not copies of the old 100-trajectory folders.

The 3-second horizon was chosen to avoid training on the clearly unstable late
portion of the earlier 30-second S63 extrapolations. It is still a synthetic
pilot horizon and must not be described as measured human-motion validity.

### Step 3 — Split by initial-condition identity

The pooled experiment assigns the initial-condition indices to 70% training,
15% validation, and 15% test sets. The same initial-condition index is never in
different splits for different teachers.

This prevents an exact initial-condition counterpart from leaking between the
training and test sets.

### Step 4 — Encode one to four observed motion windows

Each context window contains normalized:

- theta;
- x;
- estimated theta velocity;
- estimated x velocity; and
- relative time within the window.

A shared one-dimensional convolutional encoder processes each window. The
window embeddings are mean-pooled, making the encoder accept one, two, three,
or four windows.

### Step 5 — Predict the four gains

The context embedding and subject descriptors enter a gain head that predicts:

```text
Kp_theta, Kd_theta, Kp_x, Kd_x
```

It also predicts a preliminary log variance for each gain. The gain loss is a
Gaussian negative log-likelihood, so the model is penalized for both inaccurate
means and unjustified confidence.

Because only three gain anchors exist, these uncertainty values are exploratory
and should not yet be interpreted as calibrated confidence intervals.

### Step 6 — Generate trajectories with a conditional DeepONet

The DeepONet has:

- a branch network receiving gains, initial state, normalized height/weight,
  fixed Pi, and delay; and
- a trunk network receiving query time with Fourier time features.

Their latent outputs are combined to produce theta and x at every query time.
The output form hard-enforces the supplied initial position and velocity:

```text
y(t) = y0 + ydot0*t + t^2*correction(t)
```

The context is deliberately not supplied directly to the forward branch. It
must influence the generated trajectory through its estimated gains; otherwise
the network could ignore the gains and copy contextual trajectory features.

### Step 7 — Apply physics-informed training

The loss combines:

1. trajectory reconstruction using the true teacher gains;
2. gain negative log-likelihood;
3. forward consistency using the context-predicted gains; and
4. delayed cart-pole physics residuals.

The physics loss uses differentiable finite differences at 100 Hz. It evaluates
the same two cart-pole equations and delayed feedback force used by the source
pipeline. Finite differences were selected for this first implementation to
reduce second-order autodifferentiation cost and improve Apple-silicon
compatibility.

### Step 8 — Evaluate few-shot behavior

The test set is evaluated using 1, 2, and 4 context windows. The code reports:

- normalized gain RMSE;
- predicted mean and uncertainty for every gain;
- theta forecast RMSE in degrees;
- x forecast RMSE in centimeters;
- oracle forward error when the true gains are supplied; and
- a training-mean-gain baseline; and
- error curves as the number of windows increases.

The oracle error separates two sources of failure:

- forward-operator approximation error; and
- gain-estimation error.

The mean-gain baseline tests whether the context encoder actually extracts
useful motion information. A few-shot model that does not outperform this
baseline is not yet providing evidence of context-dependent gain recovery.

### Step 9 — Leave-one-teacher-out evaluation

`run_cross_teacher_tests.sh` performs three additional fits. Each fit excludes
one complete teacher checkpoint from training and tests on that checkpoint.

This is a more demanding gain-anchor test, but it is still not a new-subject
test when an S63 checkpoint is held out while the other S63 checkpoint remains
in training. Holding out S43 is the closest available subject-level test, but
it is only one subject and cannot establish population generalization.

## Completed experiments and results

The results archive contains one full pooled run and three full
leave-one-teacher-out runs. All runs used the MPS device, a fixed seed of
`20261026`, and the same 100 matched initial conditions per teacher.

### Experiment A — Full pooled model

This model was trained on all three teacher/gain anchors. Initial-condition
indices were grouped across teachers before the 70/15/15 split, producing 210
training, 45 validation, and 45 test trajectories. It therefore tests new
initial conditions for **known** gain anchors; it is not an unseen-gain or
unseen-subject test.

| Context windows | Gain RMSE | Gain baseline | Theta RMSE (deg) | Theta baseline (deg) | x RMSE (cm) | x baseline (cm) |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.065565 | 0.150660 | 1.862 | 3.416 | 7.222 | 12.242 |
| 2 | 0.011775 | 0.150660 | 1.697 | 3.416 | 1.506 | 12.242 |
| 4 | **0.006612** | 0.150660 | 1.709 | 3.416 | **1.169** | 12.242 |

At four windows, the pooled model improves normalized gain RMSE by 95.6%,
theta forecast RMSE by 50.0%, and x forecast RMSE by 90.5% relative to the
training-mean-gain baseline. Mean relative error for every predicted gain is
below 1.1%. Two windows already separate all three known anchors; the main
remaining benefit of four windows is improved gain and x accuracy.

### Experiment B — Teacher-holdout models

Each teacher-holdout model was trained on 170 trajectories and validated on 30
trajectories from the other two teachers. All 100 trajectories from the named
teacher were excluded from training and validation and used for testing.
Because the teachers share a matched initial-condition bank, corresponding
initial conditions from the two retained teachers can still appear in training;
this isolates teacher/gain-anchor transfer, not transfer to a new initial-state
distribution.

The table below reports the four-window result. Positive percentages mean the
few-shot estimate improves on the training-mean-gain baseline; negative values
mean it is worse.

| Held-out teacher | Gain RMSE | Gain change vs baseline | Theta RMSE (deg) | Theta change | x RMSE (cm) | x change |
|---|---:|---:|---:|---:|---:|---:|
| S43 chunk 1 | 0.258838 | +0.05% | 9.838 | +2.88% | 37.340 | -7.59% |
| S63 chunk 1 | 0.223938 | -26.93% | 2.659 | +32.30% | 24.155 | -6.86% |
| S63 chunk 6 | 0.224402 | +7.49% | 3.226 | +38.14% | 23.639 | +4.18% |

These runs do **not** demonstrate unseen-gain recovery. When S63 chunk 1 is
held out, the encoder predicts approximately the known S63 chunk 6 gains. When
S63 chunk 6 is held out, it predicts the low-gain S43/S63-chunk-1 region. When
S43 is held out, the unseen low `Kp_x` value cannot be reconstructed because
both remaining training teachers have `Kp_x` near 14. More context windows
produce almost no improvement in any of the three holdout runs.

Forecast RMSE can improve even when gain recovery fails because the forward
operator itself is also being evaluated outside its trained gain anchors. The
occasionally worse oracle error confirms this off-anchor surrogate error.
Consequently, holdout trajectory RMSE must not be used as evidence that the
held-out physical gains were recovered.

See `FINDINGS.md` for per-window results, predicted gains, training diagnostics,
limitations, defensible claims, and recommended next experiments.

The `teacher_vs_operator_examples.png` files already present in this archive

## Installation on an M3 Mac

Python 3.11 is recommended.

```bash
cd S43_S63_DeepONet_FewShot
chmod +x setup_mac.sh run_smoke_test.sh run_full_experiment.sh run_cross_teacher_tests.sh
./setup_mac.sh
```

The checkpoint exporter uses TensorFlow because the original models are Keras
`.weights.h5` files. The unified operator uses PyTorch and automatically selects
Apple MPS when available, otherwise CPU.

The optional Apple TensorFlow plug-in can accelerate compatible TensorFlow
operations, but the teacher-export step is small enough to run on CPU.

## Run order

First run the smoke test:

```bash
./run_smoke_test.sh
```

Smoke outputs only verify paths, checkpoint loading, tensor shapes, training,
evaluation, and plotting. They are not scientific results.

Then run the pooled full experiment:

```bash
./run_full_experiment.sh
```

If the pooled run succeeds and time permits, run:

```bash
./run_cross_teacher_tests.sh
```

## Expected compute cost

This is much cheaper than retraining the original three Stage 3 PINNs.

Approximate M3 expectations:

- setup/download: depends on internet speed because TensorFlow and PyTorch are
  large packages;
- teacher trajectory generation: usually a few minutes or less;
- smoke test: normally under a few minutes after installation;
- pooled 500-epoch experiment: roughly 10–45 minutes depending on MPS support,
  thermal state, and early stopping;
- three leave-one-teacher-out fits: approximately three times the pooled
  training cost.

These are estimates, not guarantees. The script uses only 300 short trajectories
and should fit comfortably in normal laptop memory.

To force CPU if MPS causes an unsupported-operation error:

```bash
python train_operator.py --mode full --device cpu
```

## Claims this first experiment can and cannot support

It can test whether one model can represent the three existing teacher regimes
and whether additional motion windows improve gain recovery.

It cannot yet prove:

- continuous generalization across the four-dimensional gain space;
- reliable uncertainty calibration;
- population-level control gains; or
- generalization to an unseen human subject.

Those claims require many more gain anchors and at least one additional subject
reserved entirely for testing.
